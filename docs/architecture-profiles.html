📖 什么是 Profile

Profile = 一个用户专属的 AI Agent 运行时沙箱

进程
独立 Hermes Gateway 进程
每个 Profile 在 Pod 内运行一个独立的 hermes gateway 进程，占用一个端口（8644+），进程间无任何共享状态
数据
独立 SQLite 数据库
每个 Profile 拥有独立的 state.db，存储该用户的全部会话和消息记录，Profile 间完全不可见
配置
独立环境配置
每个 Profile 有独立的 .env 和 config.yaml，可分别配置不同的模型和提示词
目录
独立文件系统
密钥、记忆、技能、缓存各自独立的目录层次，Profile 间互相隔离

🎯 解决的问题

没有 Profile 隔离 vs 有 Profile 隔离

场景❌ 无 Profile 隔离✅ 有 Profile 隔离
多用户并发共享上下文，A问"查库存"B问"今天天气"，引擎混淆上下文各自独立上下文，并行互不干扰
运营统计无法区分用户，所有消息混在一起按 Profile 粒度统计，精确到每个用户的使用量
引擎重启所有会话/记忆丢失，用户需重新建立上下文Profile 目录持久化（PVC），重启后恢复
多租户无法实现——所有用户共享引擎实例天然隔离，每个租户独立 Profile
定制化全局生效，无法按用户差异化每个 Profile 可配置不同的模型和提示词
核心价值：多 Profile 将一个"共享的引擎实例"升级为"一个引擎实例 = 多个独立 AI Agent"，实现用户级的资源隔离和数据安全。

🏗️ 系统架构

四层架构：外部 → 入口 → 编排 → 引擎

关键架构决策：Nginx 是引擎 Pod 的 Sidecar 容器，与 Hermes 引擎同 Pod。 根据请求头 X-Hermes-Profile 将请求路由到对应 Profile 的端口。

📋 Profile 类型与派生规则

INDEPENDENT（独立）vs SHARED（共享）

属性INDEPENDENTSHARED
适用范围Agent 访问范围 = ALL 或 USERAgent 访问范围 = USER_GROUP
用户关系1 个 Profile = 1 个用户1 个 Profile = 1 个用户组
数据隔离完全独立组内共享
典型场景通用 Agent，每人独立上下文门店助手，店员共享 Profile

派生规则（后端自动执行，无需用户配置）

Agent.access_scope派生 scope_type派生 profile_type含义
ALLALLINDEPENDENT全员可见，每人独立 Profile
USERALLINDEPENDENT指定用户可见，每人独立 Profile
USER_GROUPUSER_GROUPSHARED用户组可见，组内共享 Profile
def derive_scope_and_profile(agent):
    if agent.access_scope in (ALL, USER):
        return scope="ALL", profile="INDEPENDENT"
    if agent.access_scope == USER_GROUP:
        return scope="USER_GROUP", profile="SHARED"
重要：Channel 不再独立设置 scope_type 和 profile_type。创建渠道时自动从 Agent 派生，避免不一致。

🛡️ 幂等性与容错

Profile 创建是幂等的，重复请求不会产生重复 Profile

幂等创建流程

def ensure_profile(req):
    # 1. 先查数据库，按 profile_name 精确匹配
    existing = db.query(AgentProfile).where(
        profile_name=req.profile_name,
        agent_id=req.agent_id
    ).first()

    # 2. 已存在且端口有效 → 直接返回（不重复创建）
    if existing and existing.internal_port:
        return existing    # 瞬间返回，零开销

    # 3. 不存在 → 创建新 Profile
    port = allocate_port(deployment)
    create_hermes_profile(agent_id, profile_name, port)
    return {profile_name, port, created=True}
确定性命名
同名 = 同 Profile
名称含 user_id 哈希，相同用户 + 相同 Agent → 确定性的同名 Profile，天然幂等
毫秒级返回
已存在即返回
Profile 已存在时直接返回端口号，不修改数据库，不影响已有会话
恢复能力
引擎重启后自动重建
Pod 重启后 Profile 目录由 PVC 保留，只需重启 gateway 进程即恢复

🔄 生命周期管理

Agent 和 Profile 的完整状态流转

部署状态ProfileK8s Pod数据位置触发条件
PENDING—无无Agent 创建后未部署
DEPLOYING—创建中—Controller.deploy()
RUNNING活跃RunningPod 内 PVCPod 就绪
SUSPENDED已存档Scale=0MinIO30min 空闲 → 自动暂停
ARCHIVED已归档已删除MinIO 归档暂停后 24h → 自动销毁
数据持久化：SUSPEND 时引擎数据通过 kubectl exec tar 打包存档到 MinIO； DESTROY 时只清理 K8s 资源，归档数据保留在 MinIO 中可恢复。
