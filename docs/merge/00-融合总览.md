# UnionAgents 双仓融合总览

> 本目录是「Repo1(union_agent, V1) × Repo2(union-agents, V3) 融合」的执行文档。
> 最终代码并入 **Repo1 的 `develop` 分支**。三团队并行，按 `01-接口契约.md` 对齐。

## 1. 背景

两仓同源，分两团队演进后偏差：Repo2 已到 V3 三层架构 + 147 项特性（见 `docs/features/full-feature-catalog.md`，**特性基线以 Repo2 为准**）；Repo1 仍 V1 单 Agent 架构，但做了大量特性细化（hub 能力中心、Dify 引擎、审批工作流、adapter 多引擎协议归一化、端体验打磨）。

## 2. 目标架构（3 服务）

| 服务 | 端口 | 来源 | 职责 |
|---|---|---|---|
| **manager** | 8002 | Repo2 V3 + Repo1 controller 并入 | V3 三层（定义/版本/资源池/实例）+ LiteLLM 模型网关 + RBAC/UserGroup + dashboard/metrics + **K8s 生命周期 worker**（原 controller 全部职责 + recycle_scheduler/metric_sampler 后台） |
| **gateway** | 8010 | Repo2 gateway + Repo1 adapter + Dify | **chat 代理（adapter 机制：Hermes/Dify/OpenClaw 三引擎协议归一化）** + SSE 流式 + IM 渠道分发（feishu/wecom/dingtalk）+ 权限闸门 + 引擎健康检查/降级 |
| **hub** | 8003 | Repo1（独立服务，独立 DB） | 能力中心：hub_item 版本/审批记录/安全扫描/标签/生命周期 |

端口规划：PostgreSQL 5432 / MinIO 9000-9001 / LiteLLM 4000 / Hermes 8642 / Dify 8080 / Manager 8002 / Gateway 8010 / Hub 8003 / Admin 8848 / Portal 3000。

## 4. 融合策略

1. **建基座**：Repo1 `develop` 上用 Repo2 覆盖 `services/`(manager/controller/gateway)、`apps/`、`pkg/`、`scripts/`、`deploy/`；移除 Repo1 V1 的 `services/manager`、`services/controller`、`services/llm-gateway`、`services/channel-gateway`（细化逻辑按任务书选择性移植）。
2. **并入 controller**：Repo2 `services/controller/app/*` → `services/manager/app/worker/`；删 manager 侧 `controller_client` HTTP 封装改进程内直调；保留 `/api/controller/*` 路由前缀由 manager 挂载。
3. **嫁接 Repo1 细化**：按团队任务书逐项移植。
4. **数据迁移**：复用 Repo2 `scripts/migrate_to_v3*.py`（V2→V3）；新增 V1→V3 映射（Agent→Definition+Version+Instance；AgentChannel→AgentInstanceChannel；ApiKey→LiteLLM virtual key）。

## 5. 团队划分

- **A 后端核心**（manager + controller 并入）：关键路径，最先开工。任务书 `team-A-后端核心.md`。
- **B 网关/渠道/Dify/hub**：强依赖 A 契约，可先 mock。任务书 `team-B-网关渠道Dify-hub.md`。
- **C 双前端**（Admin + Enduser）：依赖 A+B 契约，可先 mock。任务书 `team-C-双前端.md`。
- 接口契约：`01-接口契约.md`（A 在 W1 冻结，B/C 据此 mock）。

## 6. 并行时序

```
W1   A 冻结数据模型 + API 契约 + DNS 命名 ──┬─→ B/C 按契约 mock 开工
     A 基座可启 + controller worker 并入      │
W2~3 A 三层/LiteLLM/RBAC/dashboard          ├─→ B adapter+Dify+IM+hub接入；C 前端基座+页面
W4   A 迁移脚本 + 知识库占位确认             ├─→ C 嫁接 Repo1 细化
W5   三方联调：前端→gateway→manager→worker→K8s；IM 端到端；Dify 链路
W6   数据迁移演练 + 全特性核对(147 + Repo1细化) + 上 develop
```

依赖与解耦：A「模型+API 契约」是关键路径，W1 必须冻结；controller 并入后 gateway 仍走 `/api/controller/*`，B 无需改调用方；hub 独立 DB 不阻塞 A；知识库本次不做（双方均无后端）。

## 7. 必须遵守的约束

- Gateway 反向依赖禁止：仅靠 `X-Agent-ID` + DNS 命名，不查 Controller（controller 并入后仍成立——gateway 不查 worker）。
- SSE：`proxy_buffering off`；不缓冲/修改 SSE；不用 `Connection upgrade`；浏览器 ReadableStream+TextDecoder。
- Gateway Origin/Referer 过滤（adapter `transform_headers` 已实现）。
- 存档提前到 SUSPEND（30min）；不定期轮询备份；PVC 实时写；DESTROY 仅清 K8s。
- 会话不入 manager DB（engine 自管 / gateway SQLite 兜底）。
- UserGroup 最小隔离单元；LiteLLM 唯一出口；每 Agent 一 key。
- 开源引擎不侵入，容器化 + 原生 HTTP API。
- Admin 样式约束（CLAUDE.md：`<div class="main">`、图标 `~icons/ri/` 导入、ECharts `as any`、搜索框 260px、改 yaml 需重启 Vite）。
- 敏感信息只走 env/k8s Secret/.env.local（已 gitignore）；示例文件用占位符。

## 8. 验证（端到端，10 项）

1. 基座可启：k3s 起 manager+gateway+hub；`/health` 三服务 200；seed 幂等。
2. 三层链路：Admin 建定义→发布版本→建资源池→建实例→上线；deploy SSE 进度可见；Pod RUNNING。
3. chat 代理三引擎：Hermes 流式回；Dify 验证 OpenAI↔Dify 请求体/SSE 转换；OpenClaw 同理。
4. 生命周期：suspend(30min 存档)→resume→destroy(归档)；dashboard 指标可见。
5. IM：企微/飞书/钉钉回调→权限闸门→流式回复（飞书卡片编辑、企微 2048 分段）。
6. hub：导入→审批→安全扫描→发布→发现；组隔离。
7. 知识库：占位页可访问（本次不做真实功能，见决策表）。
8. 审批工作流：Enduser 触发需审批操作→ApprovalCard→中断恢复(resumePendingHermesRuns)。
9. 数据迁移：V1→V3 演练，一致性核对。
10. 特性核对：逐项打勾 Repo2 catalog 147 项 + Repo1 细化清单。
