# 设计哲学与红线

> **读者**：贡献者 / 架构师 / 想理解设计背后工程教训的读者
> **预计阅读**：10 min

开源版 Palantir 的三层分离、ICD 接口契约、可替换组件、命名规范、两层正交——这些不是"设计出来"的，是"长出来"的。每一条设计原则背后都有一个真实的坑——踩了、痛了、修了、然后抽象成原则。这份文档把原则和它们背后的故事放在一起，帮助理解"为什么要这样"而不是"规定是什么"。

## 四条设计哲学（从 overview 整体往下看）

前面四篇文章——从 Palantir 到开源版、架构总览、本体体系、数据流场景——讲的是"开源版 Palantir 做什么、怎么做"。这四条哲学回答"为什么是这样做而不是另一种方式"。

### 第一：把复杂留给自己

说人话：系统内部的复杂度不应该泄露给用户。用户看到的是一套业务语言描述的对象、关系、操作——背后是多个引擎、多张数据库表在协同工作，但这不是用户需要知道的。

怎么做到的：本体统一抽象。`query_with_dataframe` 一个工具背后可能拆成了 PG 查属性 + Neo4j 图遍历 + PostGIS 空间过滤 + TimescaleDB 时序聚合——但调用者只传一份 IR，拿回一份结果（带 evidence_id 可追溯）。

### 第二：组件复用最大化

说人话：同一段逻辑不写两遍。工具层的工具同时服务三个入口（MCP、AG-UI、REST），改一处三端生效。前端 ObjectCard 组件在列表、图谱、详情弹窗、编辑表单四个地方复用——不只是省代码，更是保证"同一个对象在不同上下文里看起来是同一个东西"。

这是平台化的工程基础。如果每个消费端都自己封装一套逻辑，改一个规则要改三份代码，平台就不是平台——是三个独立的项目凑在一起。

### 第三：先走通再完美

说人话：不要在设计阶段穷尽所有可能性。先把最小闭环跑通，在运行中观察"哪里最疼"，在痛点处深化抽象。

例子：ObjectSet IR 不是一开始就设计出来的。是在 TextQL 反复踩坑之后（LLM 直出 SQL 出错率太高、跨引擎查询每次都写新逻辑）才抽象出来的。outbox 同步机制是 CDC 链路出了三次生产故障之后重新设计的。但这些"事后抽象"比"事前设计"更健壮——因为它们是基于真实故障长出来的。

### 第四：前端质量守则

每一条都来自真实事故：`tsc` 通过的代码 `vite build` 不过（async onClick）、IME 中文输入被打断（受控 input composition）、图标渲染失败（字符串传给组件而非 icon 对象）。这些规则的意义是：**少给自己添不必要的麻烦**。

## 八条架构红线（每条背后都有一个坑）

红线不是建议——是**违反后整个架构会逐渐腐烂的底线**。

### ① 分层边界不可逾越

Gravitino 只管物理资产，PG 只存业务元数据，Iceberg 是唯一写入入口，Doris 是在线读主源，Trino 是联邦查询引擎。**每层只做一件事**。

**踩过的坑**：试过让同一个引擎既管存储又管查询——当性能不行想换的时候，发现所有业务逻辑都跟这个引擎的 API 耦合了，换不动。从那以后定了这条铁律。

### ② 可替换性靠 ICD 保障

每层只暴露一个接口契约（ICD），上层通过 ICD 调用下层。替换一层 = 实现同一个 ICD = 其他层不受影响。

**为什么重要**：不同客户现场的基础设施不同。有 Neo4j 集群的、没有的、用了 ClickHouse 的、还在用 MinIO 的。架构层的可替换性不是技术炫技——是保证一套代码适配不同部署环境的能力。

### ③ Doris 索引表名必须带本体前缀

`idx_{ont}__{type}` 格式。没有这个约束时，两套本体的 ObjectType 允许同名（两个客户都叫"订单"），数据直接互盖了。修了一周。

### ④ 物理命名用 snake_case

不是因为好看。有人把 PascalCase apiName（`FlightStatusLog`）直接转小写当物理表名——`flightstatuslog`，词界全丢。改回 `flight_status_log`——保的是"计算机能认出的词界"，人在一堆字母里也能看懂。

### ⑤ VIRTUAL 目标禁止写入

虚拟表是外部数据源的指针。写入走外部系统的链路，不经过开源版 Palantir 审计。如果有人执行了写入，系统不知道谁写的、什么时候写的、改了什么。

### ⑥ Ontology API 不接受 NL

这不是技术限制，是架构边界。如果 Ontology API 直接接受自然语言，它依赖 LLM 来把 NL 翻译成查询——LLM 出错的时候没法检测。把 NL→IR 放在 AI 层（`/ai/agent`），IR 进入 Ontology 层后被确定性校验——这层是可审计的。

### ⑦ 无 Redis

不是因为 Redis 不好，是因为开源版 Palantir 当前不需要。Doris 自带查询缓存，Doris 不可用时 Trino 降级——不需要中间再加一层缓存。每引入一个新组件，不是加了一个功能，是引入了一组新的故障面和一致性开销。在没证明必须需要 Redis 之前，不引入。

### ⑧ apiName 一旦确定不重改

displayName 可以随便改（不影+响下游）。apiName 是机器唯一键——改了所有引用全断。规则固化在 `naming.py` 里，Property/Link 规则推导，ObjectType/Action 后端校验 pattern。
