## 一、背景介绍：企业数据平台的瓶颈与 Palantir 的回答

### 1.1 传统数据架构的尽头是"看见但做不到"

过去二十年，企业花大力气建数仓、上 BI、做数据中台。结果是什么？数据确实能查了，报表确实好看了，但**从"看见问题"到"采取行动"之间，隔着会议、邮件、跨系统操作**。决策本身的上下文也没有沉淀——为什么这么决定、当时评估了哪些方案、结果怎么样——全在人的脑子里或邮件里，系统不知道，也没法学习。

举一个具体的例子。一家航空公司，某架飞机的发动机传感器读数异常。传统方式下，需要人打开四个系统：传感器数据在时序库里，维护记录在工单系统里，备件库存和采购信息在 ERP 里，航班调度在运控系统里。数据都在，但**它们之间的关系靠人来串联**——人把"传感器读数异常"理解成"可能要停飞检修"，再查"停飞检修"意味着哪些航班受影响，再查受影响的旅客怎么办。每一步都是人工跨系统搬数据、做关联。周期以小时甚至天计。下次换个工程师又得重来一遍。

问题不是数据不够、也不是查得不够快，而是**数据、逻辑、动作是割裂的**。数据在数仓里，业务规则散在各个应用代码里，执行要回到业务系统里，安全策略在网关上。这四样东西分属不同系统，链路是断的，只能靠人来衔接。

### 1.2 Palantir 的回答：本体是组织的数字孪生

![数据、逻辑、动作、安全四要素合到同一模型](./palantir-data-logic-action.jpg)

Palantir 的解法是把数据、逻辑、动作、安全合到同一个模型里——**本体（Ontology）**。本体不是数据字典，不是 ER 图，是**组织的数字孪生**：一个"发动机"不是一个数据库行，是一个完整的对象，带着型号、服役时间、维护历史、关联的传感器、装在哪架飞机上，同时也带着"这台发动机能做什么操作"（比如"申请停飞检修"）和"谁能看到它的什么数据"。

回到发动机的例子。传感器读数异常进来后，系统沿本体里预设的关联链自动遍历：传感器→发动机→飞机→航班→旅客，整个过程不需要人切换系统。如果决定停飞检修，这个"决定"不回到别的系统里执行——它直接在本体里触发一个 Action，原子地更新航班状态、通知旅客、调整后续航班、写审计日志，一个事务内完成。

这就是 Palantir 和传统数据平台的本质区别：**不是你查数据更快，是系统把数据、推理、执行闭环了。** 传统 BI 是"看见就完了"，Palantir 是"看见→决定→执行→学习"。

### 1.3 安全是原生的，建模即工具

正因为动作能直接执行到业务系统，安全就变成了生死问题。Palantir 的安全模型是架构级、预防性的：读操作自动过滤权限，写操作强制三重校验（权限、参数合法性、业务规则），全链路自动血缘不可变。这些不是建议，是硬编码在引擎里的，大模型也绕不过去。

还有一个容易被忽视的设计：**你定义了本体，工具就自动生成了**。定义一个对象类型，对应的查询、过滤、遍历工具自动就绪；定义一套操作规则，对应的执行工具自动就绪。本体改了，工具自动更新。这一点到了 AI 时代尤其重要——大模型要操作企业数据，靠的就是这些工具，工具和本体同源，AI 才不会拿着过时的认知去执行。

## 二、痛点与机遇：为什么现在做

### 2.1 痛点：项目经验缺少沉淀为平台能力的路径

Palantir 的范式是对的，但它在国内市场无法直接使用。国内做企业数据项目，常见的困境是项目做得深，但缺少抽象的产品架构和平台基础，阻碍了可复制的垂直行业 know-how 沉淀。**每个项目从零搭架构，行业经验沉淀在人的脑子里或项目文档里，下一行业、下个项目很难复用。**

### 2.2 机遇一：用 AI 增强交付，从 FDE 到 AI FDE

Palantir 交付项目的速度是它商业成功的关键——传统 IT 合同要走 6-12 个月的 PoC，Palantir 靠 Bootcamp 压缩到 5 天。能这么快，是因为它把 AI 用到了交付本身：AI FDE（前方交付工程师）是一个嵌在平台里的 Agent，FDE 用自然语言跟它对话，它就能做数据集成、本体建模、函数创建、治理审计，原本要人工干一周的活几天甚至几小时完成。

**一套好的平台，不光要有本体架构，还要有"AI 贯穿交付"的能力——否则再好的架构，交付跟不上也走不进行业。**

### 2.3 机遇二：大模型时代，企业 AI 需要一个"可信操作台"

大模型的成熟给 Palantir 范式加了一个关键变量。在本体架构里，大模型需要理解企业数据 → 本体的语义层给了它"业务语言"；大模型需要操作企业数据 → 本体的工具层给了它"可调用原语"；大模型需要被约束 → 本体的安全层给了它"不可逾越的边界"。**本体解决了 LLM 在企业落地最大的两个问题：幻觉（语义锚定）和越权（安全内建）。**

而且 Palantir 最早是给军工和航空做的，这些行业对"出错"的容忍度为零。一个被这些行业验证的安全模型，对企业 AI 场景的安全需求是够用的。数据主权始终在企业手里，AI 在受控范围内做推理和执行。

### 2.4 机遇三：平台基座是 FDE 飞轮的前提

Palantir 的核心竞争力不仅在于技术，更在于它的商业模式——FDE 在前线交付、PD 把验证过的能力回流产品，形成不断加速的飞轮。而支撑这个飞轮的，是一个统一的本体平台基座。

开源版 Palantir 是一次抛砖引玉的探索——由 FDE 在前线识别痛点和需求，通过技术规划和选型验证本体平台的可行性，为关键难题提供技术和资源支持。最终期望是公司层面能有一个统一的平台基座，将开源版 Palantir 验证过的经验和能力沉淀合入，推动产品竞争力提升。

## 三、解决方案：开源版 Palantir 的设计要点

以下从架构设计思想的角度归纳几个关键决策，每一条背后都有对标的 Palantir 设计理念。

### 3.1 场景体验：从供应商停产看差异

讲太多概念不如看一个具体场景。供应商停产，需要评估影响范围和处理方案。

在传统系统里：采购员先去供应商系统查供哪些零件 → 再去 ERP 查用在哪些产线 → 再去订单系统查在途订单 → 人工汇总 → 发邮件通知客户。每一步都是人在跨系统搬数据。

在开源版 Palantir 里：

```
供应商停产事件进入系统
  → 系统沿业务关系自动遍历：供应商 → 零件 → 产线 → 订单 → 客户
  → 自动生成受影响订单清单
  → AI 提议处理方案（如"触发延期通知"）
  → 系统校验：该不该做 / 参数对不对 / 符不符合业务规则
  → 通过 → 执行，并同步更新所有相关数据
  → 全过程留下审计记录
```

关键区别：**关联是系统做的**（关系在建模时已定义好），**AI 能提议但不能越规则**（强制三重校验），**执行原子完成不留半截状态**。

### 3.2 分层架构：智能决策层 → 本体语义层 → 业务数据层

这种体验的背后，是三层架构在协同：

```
智能决策层  ← AI Agent · TextQL 自然语言查询 · 图关联推理 · HITL 审批
本体语义层  ← ObjectType / Property / LinkType / ActionType（把"表和列"翻译成"对象、关系、规则"）
业务数据层  ← Dataset（Iceberg）· Index（Doris）· Engine（Trino）· Graph（Neo4j）· GeoTime（PG）
```

三层不是技术组件的堆叠——是**抽象层次的递进**。同一份数据，在业务数据层是 Iceberg 表的若干列，在本体语义层是"供应商"对象的"产能"属性，在智能决策层是 AI 推演"供应商停产影响范围"时的输入。

### 3.3 多模型混合存储：不是"一库打天下"

Palantir 的本体存储 OSv2 是一套**多模型混合存储**体系——针对不同访问模式用不同的专用对象库并行工作。开源版 Palantir 用以下开源组合复现这套体系：

| Palantir OSv2 的存储类型 | 开源选型 | 关键选型理由 |
|:--|:--|:--|
| 属性图核心存储 | Neo4j | 多跳关系遍历不能靠表 JOIN |
| 时序存储引擎 | TimescaleDB（PG 扩展） | 超表自动分区，与元数据库同库 |
| 空间地理存储 | PostGIS（PG 扩展） | 与 PostgreSQL 同库，不跨库 JOIN |
| 数据虚拟化层 | Trino | 40+ 数据源原生连接，Doris 不可用时的降级路径 |
| 倒排属性索引 | Doris | 倒排+向量双索引，在线读主源，亚秒出结果 |
| 写入编排与同步 | SeaTunnel | 原生 Iceberg connector（仅外部源→Iceberg 搬运；Iceberg→Doris/Neo4j/PostGIS 由 ObjectIndexFunnel 直连） |
| 物理资产注册与权限 | Gravitino | Iceberg REST Catalog 原生支持 |

**没有一种数据库能同时做好事务、分析、图遍历、空间查询和时序窗口。** Palantir 的架构洞察就是承认这个事实，用多引擎协作代替单一引擎全能。同一份数据在不同引擎里有不同投影，本体语义层把它们映射回统一对象。

### 3.4 读写分离与 Action 闭环

- **读路径**：查询请求 → MANAGED 走 Doris（主路径，亚秒）→ Doris 挂了自动降级 Trino 扫 Iceberg；VIRTUAL 走 Trino 联邦。降级对调用方透明。
- **写路径**（Action 闭环）：Action 执行 → 三重校验 → PG 原子写入 `object_state` + outbox → 后台消费 outbox → Doris upsert（≤1s）+ Iceberg MERGE（≤5min）。outbox 驱动同步比额外维护一套 CDC 管道更简单可靠。

### 3.5 组件的可替换性与接口契约

开源组件可能在某些环境被云服务替换（如 Doris→DWS、Neo4j→GES、RustFS→OBS）。架构层通过**接口契约（ICD）**保证可替换性：每个组件对外暴露一组明确的方法签名，上层只通过这组签名调用。换引擎 = 实现同一组接口 = 上层代码不动。目前已定义 5 个 ICD。

### 3.6 当前状态

开源版 Palantir 不是一份设计文档，是一套已经跑起来的系统。当前状态：

- **本体语义层**已完整落地：ObjectType / Property / LinkType / ActionType 的 CRUD、数据映射、三层命名规范、对话式建模（AI 推导 apiName + 用户可改 + 后端校验）。
- **业务数据层**多引擎投影已接通：PostgreSQL（元数据 + 操作态 + outbox）、Iceberg（全量明细 + 快照）、Doris（在线读主源）、Trino（联邦查询 + 降级）、SeaTunnel（外部源→Iceberg 搬运）、Neo4j（图遍历）、PostGIS + TimescaleDB（时空分析）。Doris/Neo4j/PostGIS 的写入由 ObjectIndexFunnel + OutboxExecutor 直连各引擎完成（不经 SeaTunnel）。
- **智能决策层**已接通：一组从本体定义自动派生的工具（查询 / 遍历 / 写入 / 动作执行 / 元数据编辑）、AG-UI ReAct Agent、TextQL 自然语言查询、图关联推理（ObjectSet IR 多引擎联动）、HITL 人工审批切面。
- **安全治理体系**已落地：三层 RBAC + MAC 标记 + 行/列级权限下推（Cedar 策略 → SQL 谓词注入）+ 审计日志 + JIT 访问申请。
- **前端**已有本体管理台（对象类型/属性/关系/动作的可视化建模 + 图探索画布 + 对话式 AI 建模 + 权限管理页面）。
- 后端代码超过 100 个源文件、1268 个测试函数；前端 169 个测试用例。CI 全绿。

正在推进的方向：图探索画布的决策分析能力增强、对话式建模的多轮体验打磨、权限治理的企业联邦（SCIM 对接）、全链路血缘追踪。

## 四、启发与建议：对华为 AI2B 战略的意义

### 4.1 本体体系是 AI 时代的企业数据主权锚点

华为在 AI2B 领域的核心竞争力不是单点技术，而是**客户信任**。企业愿意把核心数据交给华为的 AI 来处理，前提是数据主权始终在企业手里——数据不出去、权限不失控、操作可追溯。开源版 Palantir 的本体体系把权限、规则、审计内置在引擎层，AI 在受控范围内做推理和执行。这个架构本质上是一个**数据主权保护装置**。

### 4.2 本体积累的行业 know-how 是提升粘性的根

每做一个垂直行业项目，本体语义层都更厚一层——业务对象、关系、操作规则、安全标记都在累计。这些沉淀是可复制的，是提升客户粘性的根。而本体越厚、决策越多，对算力和存储的牵引就越强——这是一个正向业务飞轮。

### 4.3 FDE + AI FDE：华为 ToB 服务基因的技术放大

华为的 ToB 服务能力是根植在基因里的。FDE 在前线识别痛点和业务需求，AI FDE 基于本体快速推演和验证方案，两者结合让项目交付的速度和质量有量级提升。这种"本体语义层可跨行业复用 + FDE 前线识别行业差异 + AI FDE 加速交付"的组合，是华为在 AI2B 领域的差异化优势——**不是单点技术突破，而是一套可复制的交付方法论。**

### 4.4 建议：从开源探索走向公司级本体平台

短期看，开源版 Palantir 的价值在于把难题做一遍——多引擎运维、安全实现、工具链建设，这些难点在开源探索中踩过坑、积累经验，就为真正的平台化铺了路。

长期看，更期望的是公司层面能有一个统一的本体平台基座。如果没有这套架构，每个项目都在自己搭建数据-逻辑-动作的衔接，成本是线性的；而有了平台基座，每多做一个项目，边际成本递减，行业 know-how 积累加速。开源版 Palantir 验证过的能力和经验，可以沉淀合入这个平台——它是一块砖，不是终点。

## 五、问题与讨论

以下是几个值得思考和讨论的问题。**欢迎提出你的观点——同意、反对、补充都可以。**

### 关于范式

1. **"本体作为操作系统的内核"是正确方向，还是过度设计？** 有没有更轻量的方式能达到同样的"数据-逻辑-动作闭环"效果？传统的微服务 + API 网关 + 权限中台，不能达到同样目的吗？

2. **Palantir 的成功多少来自技术、多少来自商业模式？** 如果 Palantir 把本体架构开源，会不会发现它的很多客户其实买的是"FDE 在现场帮你干活"而不是技术本身？

### 关于架构

3. **多模型混合存储是长期最优解，还是阶段性的权宜之计？** 未来会不会出现一个能同时做好 OLTP、OLAP、图遍历、时序、空间的统一数据库，让这套复杂的投影体系可以被简化？

4. **接口契约（ICD）能真正实现组件可替换吗？** 理论上很漂亮，但实际中换一个引擎往往不只是改接口实现——索引策略、查询优化、运维体系都要改。有没有人在真实项目里实践过？坑在哪？

### 关于 AI 安全

5. **大模型操作企业数据的安全边界到底在哪？** AI Agent 做推理、提议动作——如果它的推理本身就是错的（不是幻觉，而是逻辑错误），安全校验能兜住吗？还是说安全架构只能防"越权"，防不了"愚蠢"？

6. **Cedar 策略引擎 + SQL 谓词下推的行级安全模型**，在复杂多表关联查询里会不会有性能天花板？业界有没有更优的权限下推方案？

### 关于产品化

7. **开源版 Palantir 的"最小可行产品"边界在哪？** 是先把本体语义 + 多引擎投影做透，还是先把 AI Agent + 对话式建模做到惊艳？在资源有限的情况下，哪个方向对客户价值的杠杆最大？

8. **FDE 的工作模式在华为能不能跑通？** Palantir 的 FDE 模式依赖硅谷的工程师文化和极高的单人产出。在中国企业市场，这种"派工程师驻场、深度绑定客户业务"的模式可行吗？
