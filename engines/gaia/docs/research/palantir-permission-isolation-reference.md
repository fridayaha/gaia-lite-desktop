## 〇、核心一句话总结

Palantir Foundry 权限体系 = **五层纵深防御 + 双轨访问控制（RBAC×MAC）+ 身份权限解耦（组为核心）+ 代码数据同栖 + 全链路审计治理**。

五个设计思想浓缩：
1. **五层纵深防御**：Org → Space → Project → Marking → 行/列，逐层拦截，单层出错不影响全局。
2. **双轨控制互补**：RBAC 管协作授权（灵活、业务自治），MAC 标记管数据强制兜底（硬门槛、合规集中管控），二者逻辑与。
3. **组为核心解耦**：身份与权限通过 Group 解耦，人员异动只调组，权限变更不碰人，治理成本与规模脱钩。
4. **代码数据同栖**：权限边界与数据生产边界对齐（Transform 代码与输出数据集必须同 Project），数据出 Project 必须显式 Reference，流动可管控可审计。
5. **审计治理兜底**：全操作强制留痕、追加写入不可篡改，配合常态化治理机制，满足合规举证。

## 一、五层隔离边界（自上而下，权限校验「与」逻辑）

> 核心原则：**串行多层拦截、默认拒绝、逐层放行、不可见即安全**。任意一层不通过直接终止，不进入下一层。

| 层级 | 名称 | 定位 | 校验逻辑 | 不通过结果 |
|:---:|------|------|----------|------------|
| 1 | **Organization（组织）** | 主体身份强隔离层（租户级 MAC） | 用户主组织 + Guest 组织集合 ∩ 资源绑定组织集合 ≠ ∅（组织标记是「或」关系） | 资源完全不可见，搜索无结果 |
| 2 | **Space（空间/原 Namespace）** | 业务域容器 + 本体生命周期载体 | 用户在空间访问白名单（组织白名单子集）内 + 拥有空间级准入角色 | 空间及内部项目全部不可见 |
| 3 | **Project（项目）** | 平台第一安全边界（DAC 最小单元） | 用户/所属组拥有 Owner/Editor/Viewer/Discoverer 之一 | 项目不可见；仅 Discoverer 可见名称无法读数据 |
| 4 | **Marking（安全标记）** | 数据级强制隔离（MAC，硬门槛） | 资源全部标记 ⊆ 用户拥有标记集合（布尔合取 AND） | 可见资源条目但无法读数据内容 |
| 5 | **行/列级安全** | 数据内容细粒度过滤（千人千面） | Restricted View 规则 + 列级标记 + 本体对象过滤 | 返回可见数据子集，无权限行/列不返回 |

> ⚠️ 关键澄清：**Organization 标记是「或」（用户持有任一即可），普通 Marking 是「且」（用户须持有全部）**——这是组织标记的特殊属性。

### 1.1 Organization 层关键约束
- 每用户**唯一主组织（Home Org）**，永久不可变更；可作为 Guest 加入多个外部组织
- 每个组织对应一个**系统级内置标记**，自动绑定该组织所有用户与资源，系统维护不可手动移除
- Guest 天然受限：不能创建组/服务账号、不能获组织管理权限、不能看目标组织全局用户目录、操作标记为「外部访问」专项审计
- 资源绑定最小单元是 **Space**，Project/Dataset 继承 Space 的组织范围，不能单独扩大
- 组织间可见性三档：完全隐藏（默认）/ 名称可见 / 完全可见，单向配置
- **跨组织唯一合法通路 = 共享空间**（双方都加白名单），无其他旁路
- 删除保护：多组织共享 Space 仅当所有组织解除/删除才级联删除

### 1.2 Space 层关键约束
- **Space 与 Ontology 一一强绑定、同生命周期**：创建 Space 自动建同名本体，Space 删除本体不可恢复，跨 Space 不能复用本体对象（Foundry 最核心约束之一）
- **基础设施不可变**：存储/计算/加密/计费创建后永久不可改
- Project 的组织白名单 ⊆ Space 组织白名单（子集约束）
- 一个 Space 只绑定一套 **Role Set（角色集）**，Space 内所有 Project 共用
- **Space 级角色全量继承**到所有 Project，Project 内无法移除/降级（叠加取最高）
- Space ID 全局唯一不可改，是资源路径根节点

### 1.3 Project 层关键约束
- 官方定义：**Projects are the primary security boundary in Foundry**
- **代码数据同栖（Code-Data Colocation）**：Transform 代码与输出数据集必须同 Project，跨项目写入由执行引擎内核拦截
- **权限全量继承**：Project 角色覆盖所有子文件夹/数据集/代码/应用/本体，**不支持子级阻断继承**；只能叠加 Marking 收紧，不能放宽
- Project 是权限计算的最小缓存单元（用户+项目+角色结果缓存，复用到项目内所有资源）
- **跨项目复用 = Reference（只读逻辑链接）**，不复制数据、只读、完整继承源安全属性、二次校验源项目权限
- 角色单向授权：高可授同等或更低，低不能反向（Owner 可授 Owner，Editor 只能授 Viewer 及以下）
- 删除进回收站默认 30 天可恢复

### 1.4 Marking 层关键约束
- **布尔合取（AND）**：N 个标记须全部持有，缺一不可；无「或」逻辑（内核级不可改）
- **血缘自动传播引擎**：层级传播（文件夹→子→文件/列）+ 血缘传播（输入→转换→输出→衍生→本体→应用→导出），取上游标记并集赋给输出
- **传播不可逆**：移除须显式 `stop_propagating([marking_id])`，且必须先脱敏/删敏感列，经标记管理员审批合并到受保护分支
- **管理权强制分离**：标记管理权（创建/删除/授权用户）仅 Marking Admin 拥有；标记使用权（给资源打标）Project Owner/Editor 可用已有标记。Project Owner 不能创建标记、不能给用户授标记权限
- 系统标记（组织标记）豁免：不受普通标记管理员管控，不可 stop_propagating
- 治理红线：**全局标记 ≤ 20 个**，分类 ≤ 3；细粒度部门/城市隔离用 Restricted View 不用标记

### 1.5 行/列级安全关键约束
- **Restricted View（限制视图）**：不带物理存储的逻辑视图，基于用户属性动态生成 WHERE 过滤，过滤下推到计算引擎
- **只读约束**：不能作为 Transform 输入（内核拦截，防过滤后数据固化失去行级保护）
- **收紧不放宽**：完全继承底层组织/项目/标记，只能进一步收紧
- **策略确定性**：基于用户属性×数据列匹配，支持 AND/OR，不支持动态脚本/外部调用
- **本体联动**：作为本体对象数据源时，对象实例可见性 = 视图行；无权限实例在图谱/搜索/应用完全不可见
- **不可绕过**：前端/SQL/API/SDK/导出全路径统一生效
- 列级三种方案：列级标记（少数高敏列）/ MDO 属性权限（本体层属性差异化）/ 转换脱敏（批量对外开放）
- 例外白名单角色严格控制人数，纳入专项审计

## 二、身份体系（三层主体，组为核心）

### 2.1 三层主体模型
```
User（自然人） → 加入 → Group（权限唯一载体） → 被授予 → 角色/标记/组织权限
                              ↑
                     Service User（非自然人）
```

| 主体 | 定位 | 核心约束 |
|------|------|----------|
| **User** | 承载自然人身份与属性，不直接绑业务权限 | 唯一主组织永久不可变；属性从身份源自动同步；分内部主用户/外部 Guest/预注册 |
| **Group** | 权限唯一承载体，角色/标记/组织权限的授予对象 | 归属唯一组织不可跨组织复用；嵌套建议 ≤ 2 层；支持从身份源同步或手动建 |
| **Service User** | 非自然人，系统集成/API/流水线专用 | 创建零默认权限须手动授；无前端登录；不能获平台管理角色；支持 Scoped 作用域 |

### 2.2 内核约束
- 用户主组织唯一不可变
- 用户组归属唯一组织，跨组织不能复用
- 组嵌套累加继承，建议 ≤ 2 层，不支持循环嵌套
- Service User 零默认权限，不继承组织默认权限
- 身份源同步的用户/组平台内不可改，以身份源为准
- Guest 不能创建组/服务账号、不能获管理权限、不能创建空间项目

### 2.3 四维分组体系（企业级标准范式）

| 维度 | 前缀 | 典型示例 | 授予权限类型 |
|------|------|----------|--------------|
| 岗位职能组 | `func_` | `func_data_engineer`、`func_finance_analyst` | 通用功能权限、基础标记权限 |
| 项目角色组 | `proj_` | `proj_finance_mart_owner`、`proj_hr_app_viewer` | 对应项目的 Owner/Editor/Viewer |
| 标记权限组 | `mark_` | `mark_pii_access`、`mark_top_secret_access` | 对应安全标记访问权限 |
| 管理职能组 | `admin_` | `admin_platform`、`admin_audit`、`admin_marking` | 平台管理角色 |

- **组授权铁律**：100% 权限授组，零直接个人授权
- 一人多组组合实现最小权限（岗位组+项目组+标记组）
- 身份源驱动自动化：核心身份全同步，平台内仅维护项目组/临时组/标记组
- 生命周期闭环：入职自动授权 → 转岗自动切换 → 离职自动失效

## 三、四级角色体系

> 角色本质 = **原子操作权限（Capability/Workflow）的预打包集合**。四级分层对应不同管理边界，**高层管理角色不自动获得低层数据访问权限**（权责分离）。

| 层级 | 角色 | 权限范围 | 权责分离要点 |
|:---:|------|----------|--------------|
| **1 全局平台** | Platform Admin / User Access Admin / Marking Admin / Audit Admin / Ontology Admin | 管整个租户的平台级能力 | 除 Platform Admin 外其他全局管理员**无数据访问权限**，管/做/审三权分立 |
| **2 空间/本体域** | Space Owner/Editor/Viewer/Discoverer + Ontology Owner/Editor/Viewer/Discoverer | 管单个业务域 | Space 角色自动继承到所有 Project |
| **3 项目基础** | Owner / Editor / Viewer / Discoverer | 管单个协作项目（最常用） | 代码数据同栖；权限全量继承不可阻断 |
| **4 应用操作** | Workshop/Action/Workflows 自定义角色 | 管单个业务操作 | 数据查看权与业务操作权分离（能看不能改、能操作不能改配置） |

### 3.1 项目四角色权限明细
| 角色 | 核心权限 | 不能做 | 适用人群 |
|------|----------|--------|----------|
| **Owner** | 项目全权管理：增删角色、删项目、管服务账号、配置标记/分支保护/审批流、所有 Editor 权限 | 不能授超项目范围权限、不能建新标记 | 项目负责人（每项目 2-3 人） |
| **Editor** | 创建/编辑/删除数据集代码流水线、运行转换、开发应用、打已有标记、授 Viewer 及以下 | 不能删项目、不能授 Owner/Editor、不能改项目核心配置 | 数据工程师/分析师/开发 |
| **Viewer** | 浏览数据、看报表应用、看血缘、导出（需额外开启）、提交访问申请 | 不能修改/运行流水线/授权 | 业务人员/一线员工 |
| **Discoverer** | 仅可见资源名称与血缘、可搜索 | **完全不能看数据内容**、不能操作 | 全局治理/审计/平台运维 |

### 3.2 角色集（Role Set）机制
- 默认角色集：平台预置，所有组织默认可用，平台升级自动更新
- 自定义角色集：企业自建，可新增/修改角色，适配自有职级体系
- **~~冻结机制~~（❌ 错误，已修正）**：原记录称「自定义角色集发布后冻结，平台新增原子权限不会自动同步，须手动添加」——**官方文档核查后修正**：
  - 官方原文（[Manage roles](https://palantir.com/docs/foundry/platform-security-management/manage-roles/)）：「when copying the Project default role set or another role set that depends on the Project default role set, the newly copied role set will be **automatically updated with any role updates to the Project default role set**. As Foundry development continues, new roles may be added by Palantir; receiving these permission updates automatically can reduce future administrative work.」
  - **正确机制**：复制自 Project default 的自定义 role set **会自动同步**平台新增角色/操作；只有完全独立（非复制自 Project default）的 role set 才不同步
  - 原材料「冻结不同步」的说法是**过度演绎/错误**，长期不维护导致功能缺失的风险被夸大
- 一个 Space 只能绑定一套角色集（官方：Role sets can only be applied at the space level）
- 权限单向递增：高角色完全包含低角色，无交叉
- 管理权限与数据权限天然分离（不自动获得，须同时授予两类角色）

### 3.3 设计哲学
- 最小权限：默认最低，按需升级
- 权责分离：管权限的不看数据、看数据的不改权限、审计的不碰业务
- 高权限角色双人负责制
- 关键操作（导出/删除/标记移除/高危 Action）单独授权，不打包基础角色

## 四、中心化授权引擎（执行中枢）

### 4.1 四大设计原则
1. **默认拒绝（Deny by Default）**：白名单机制，未显式授权一律拒绝，不可关闭
2. **串行纵深防御**：固定优先级逐层校验，任一层不通过终止
3. **不可见即安全（Security by Obscurity）**：无权限资源在前端/搜索/API/SQL 完全隐藏，不提示「无权限」，防枚举探测
4. **全路径统一入口**：前端/SQL/API/SDK/流水线/导出共用一套校验逻辑，无旁路

### 4.2 引擎六大模块
身份认证模块 / 属性解析模块 / 资源解析模块 / 策略执行模块 / 缓存模块 / 审计模块（异步落盘）

### 4.3 七层校验完整链路
```
身份认证 → 组织校验 → 空间校验 → 项目RBAC → Marking强制 → 细粒度行/列 → 操作权限
```
- 跨项目引用：执行**两次完整校验**（目标项目 + 源项目组织/项目/标记三层），全过才返回数据，安全属性以源项目为准
- 所有访问入口（前端/SQL/API/SDK/流水线/导出）走同一引擎，前后端权限完全一致

### 4.4 三级缓存体系
| 层级 | 内容 | 生命周期 | 失效触发 |
|------|------|----------|----------|
| 用户属性缓存 | 组/角色/标记/扩展属性 | 会话级+短TTL | 组/角色/标记变更 |
| 资源属性缓存 | 组织/空间/项目/标记/权限配置 | 长 TTL | 资源权限/标记变更 |
| 授权结果缓存 | 用户+资源+操作结果 | 短 TTL | 任一方变更 |

- **主动失效（主）+ TTL 兜底（次）**：变更同步失效缓存，极端失败最多几分钟自动同步
- **高敏操作缓存豁免**：权限变更/数据删除/标记移除/审计查询强制实时校验，不走缓存
- 故障降级：安全优先，默认拒绝所有访问，绝不因故障放开

### 4.5 Check Access 可解释性工具
输入任意用户+资源+操作 → 展示每层校验通过/拒绝状态 + 权限来源（哪个组/角色/标记）+ 缺失权限项 + 授权模拟

## 五、审计与治理体系

### 5.1 审计内核约束
- **强制开启不可关闭**：无全局开关，任何服务/操作必须留痕
- **追加写入不可篡改**：只能新增，不能修改/删除/覆盖，无任何接口/角色可清理
- **审计权限严格隔离**：仅 Audit Admin 看全平台；Project Owner 看本项目；组织管理员看本组织；普通用户看自己；Service User 无审计权限
- **全链路无死角**：覆盖所有操作类型/主体类型/访问路径
- **分级留存**：高风险操作永久留存，普通操作有最低留存期，归档可检索不销毁

### 5.2 审计事件六大分类
身份认证类（中）/ 权限变更类（高）/ 数据访问类（中）/ 数据操作类（高）/ 管理操作类（极高）/ 应用操作类（中）

单条日志字段：事件ID/时间戳/类型/结果 + 主体（用户/IP/UA/请求ID）+ 客体（资源路径/ID/类型/所属项目空间组织）+ 上下文（参数/变更前后/权限来源/审批单号）+ 安全属性（风险等级/是否高危/是否外部/是否异常）

### 5.3 六大治理工具
1. **标记影响分析**：打标/去标前模拟血缘传播范围，评估下游业务影响
2. **权限自助申请与审批工作流**：线上化标准化留痕，自动授权+到期回收，替代线下邮件
3. **过度权限与僵尸权限分析**：基于审计日志识别长期未用权限/超范围授权/人员异动残留/服务账号超权，输出回收建议
4. **目的访问控制 PBAC**：访问高密级数据强制选访问目的，审计绑定使用场景，异常目的告警
5. **权限健康度评估**：直接授权占比/高权限人数占比/僵尸权限比例/申请合规率/标记覆盖率
6. **定期评审机制**：月度高危复盘 / 季度高权限评审 / 半年度健康度评估 / 年度合规审计

### 5.4 高危操作实时告警清单
平台/标记管理员授予、绝密机密标记批量授予、标记移除、大批量数据导出、项目/空间/组织删除、非工作时间高权限操作、服务账号异常访问、权限批量变更、审计配置修改、Guest 高权限授予

### 5.5 自动化权限生命周期闭环
入职（HR→身份源→自动加职能组→获标准权限）→ 转岗（部门/岗位变更→自动移出原组加入新组）→ 离职（HR 标记→禁用账号→移出所有业务组→权限即时失效）→ 临时权限到期自动回收

## 六、典型落地架构（集团级模板）

### 6.1 五层 + 身份 + 角色 + 治理 标准模板
| 层 | 划分方案 | 说明 |
|----|----------|------|
| 组织层 | 1 内部主 Org + N 外部合作方 Org + 1 绝密业务 Org | 内部员工统一主 Org，外部一主体一 Org |
| 空间层 | 按业务域划分（财务/人力/生产/供应链/风控/共享协作） | 每域独立本体，跨组织协作单独建共享空间 |
| 项目层 | 每业务域按数据四层分层拆项目（原始/清洗/指标/应用）+ 高敏业务独立项目 | 越往上层权限越开放，越往下层越收敛 |
| 标记层 | 密级 4 级（公开/内部/机密/绝密）+ 敏感类型 3 类（PII/财务/法务）+ 区域标记 | 全局 ≤ 20 个，合规团队集中管控 |
| 身份层 | 四维分组（func_/proj_/mark_/admin_） | 100% 组授权不授人 |
| 角色层 | 默认角色为主，少量自定义应用角色，三权分立 | 管理与数据权限严格分离 |
| 治理层 | 月度/季度/半年度/年度四级评审 | 常态化运营 |

### 6.2 数据四层项目架构（企业级标准）
| 层级 | 命名 | 内容 | 权限 | 角色 |
|------|------|------|------|------|
| 原始接入层 | `xxx-raw` | 原始数据源接入 | 最严 | 数据工程团队 Editor，其余无 |
| 清洗加工层 | `xxx-clean` | 清洗标准化中间结果 | 较严 | 数据团队 Editor，分析师 Viewer |
| 指标汇总层 | `xxx-mart` | 业务宽表指标汇总 | 较开放 | 分析师 Editor，业务 Viewer |
| 业务应用层 | `xxx-app` | 报表应用 Action | 最开放 | 产品开发 Editor，全员 Viewer |

### 6.3 不同规模适配
- **中小团队（<50 人）**：1 主组织 + 1 默认空间 + 核心项目拆分 + 2-3 个核心标记 + 基础职能组 + 季度巡检
- **中大型企业（50-500 人）**：完整五层 + 三维标记 + 组授权铁律 + 三权分立 + 季度评审 + 身份源自动化
- **集团/强监管**：子公司/涉密独立组织 + PBAC + 行级+列级+标记三层防护 + 服务账号 Scoped + 全量审计对接 SOC + 第三方审计

## 七、十大反模式（避坑指南）

| # | 反模式 | 后果 | 正确方案 |
|---|--------|------|----------|
| 1 | 用组织替代部门级内部隔离 | 跨部门协作成本极高，本体碎片化，数据孤岛 | 内部部门用项目+标记，组织只做主体级隔离 |
| 2 | 外部用户直接加入内部主组织 | 外部用户可搜全公司员工目录，审计无法区分内外 | 外部主体独立组织，通过共享空间协作 |
| 3 | 组织间可见性全开 | 失去租户隔离意义，钓鱼/社工风险 | 默认完全隐藏，仅协作开名称可见 |
| 4 | 一个业务域拆多个空间 | 本体碎片化，同业务对象重复定义，血缘断裂 | 同业务域统一一个空间，内部用项目拆 |
| 5 | 用空间做项目级细粒度隔离 | 空间数量爆炸，本体重复建设 | 细粒度用项目和标记 |
| 6 | 共享空间放全量原始数据 | 外部组织可接触全量内部数据，泄露风险大 | 共享空间仅放加工后最小必要数据 |
| 7 | 超级大项目一锅炖 | 泄露半径极大，一人有权看全量，无法细粒度管控 | 按权限边界拆项目，有差异就拆 |
| 8 | 代码和输出数据分属不同项目 | 执行引擎拦截，权限血缘断裂 | 代码与产出必须同 Project，跨项目用 Reference |
| 9 | 试图用文件夹做细粒度权限隔离 | 项目内权限全继承，文件夹只能加严标记不能阻断角色 | 有权限差异就拆新项目 |
| 10 | 标记粒度过细（每部门一标记） | 管理复杂度爆炸，组合后权限校验复杂 | 标记 ≤ 20 个只做分类分级，部门级用 Restricted View |
| 11 | 只去标记不去敏感数据 | 严重合规违规，敏感数据裸奔 | stop_propagating 必须配合数据脱敏/列删除 |
| 12 | 项目 Owner 自行给用户加标记权限 | 违反权责分离，强制管控形同虚设 | 标记权限统一安全/合规团队管理走审批 |
| 13 | 直接给个人授角色/标记 | 僵尸权限泛滥，审计困难 | 100% 组授权 |
| 14 | 服务账号授 Owner 角色 | 密钥泄露可篡改数据改权限 | 默认 Viewer，确需 Editor，严禁 Owner |
| 15 | 多系统共用一个服务账号 | 无法区分操作主体，审计追溯难 | 一用一号独立管控 |
| 16 | 组嵌套过深（≥3 层） | 权限来源不透明，意外越权 | 嵌套 ≤ 2 层扁平化 |
| 17 | 在前端应用层做数据过滤 | 完全可绕过（抓包/改参数/直接 API），虚假安全 | 必须在底层（标记/行级视图）强制拦截 |
| 18 | Restricted View 作为转换输入 | 内核拦截或权限血缘断裂失去行级保护 | 直接读展示，不固化成物理数据集 |
| 19 | 为每个团队复制数据集实现行隔离 | 数据冗余，口径不一致，维护成本高 | 一份底层 + 一个 Restricted View |
| 20 | 行级规则依赖手动维护的用户属性 | 人员转岗属性更新不及时，越权或失效 | 属性从身份源自动同步 |
| 21 | 全员默认 Editor | 过度授权，误操作/篡改风险 | 默认 Viewer/Discoverer，按需升级 |
| 22 | 平台管理员同时有高数据权限 | 权力过度集中，内部风险，合规不过 | 严格三权分立，账号分开 |
| 23 | 自定义角色泛滥每项目一套 | 管理爆炸，审计困难，升级遗漏 | 全局统一默认角色集，差异化用标记/行级/应用角色补充 |
| 24 | 自定义角色长期不更新 | 平台升级后功能缺失/安全漏洞 | 每次大版本更新同步对比更新 |
| 25 | 审计只存不看 | 异常无法及时发现，合规摆设 | 月度复盘 + 高危实时告警 + 有人闭环 |
| 26 | 权限只增不减永久授权 | 僵尸权限累积，最小权限失效 | 定期评审 + 自动到期 + 僵尸识别 |
| 27 | 依赖缓存延迟做临时权限 | 主动失效近实时生效，高敏不走缓存 | 靠正式授权配置 |
| 28 | 跳过外层校验只判内层 | 纵深防御失效，元数据泄露 | 多层配合，外层粗粒度内层细粒度 |
| 29 | 例外白名单全员 | 行级安全形同虚设 | 例外角色严格控制人数专项审计 |
| 30 | 为合规牺牲业务过度设计 | 业务绕开平台走线下，越管越乱 | 安全与效率平衡，自动化优先人工审批为辅 |

## 八、权限安全成熟度模型（L1-L5）

| 等级 | 特征 | 关键标志 |
|------|------|----------|
| **L1 初始级** | 项目随意建，权限直接给个人，无审计无治理 | 靠人工管理全凭自觉 |
| **L2 基础级** | 有基本项目拆分，组授权，基础审计 | 权限可管理，操作可追溯 |
| **L3 规范级** | 五层架构完整，标记体系完善，权责分离，定期评审 | 安全有兜底，治理有机制 |
| **L4 优化级** | 权限生命周期自动化，自助申请+审批，过度权限分析，异常告警 | 效率与安全平衡，治理自动化 |
| **L5 卓越级** | 智能权限推荐，异常访问自动检测，动态自适应权限，零信任 | 主动防御，持续优化 |

## 九、与 Gaia 现状的差距速记（设计时的对照锚点）

> 详见 [`palantir-capability-gap-analysis.md`](./palantir-capability-gap-analysis.md) §三 P0-B。此处仅速记对照点，Gaia 设计文档另立。

| Palantir 能力 | Gaia 现状 | 差距本质 |
|---------------|-----------|----------|
| Organization 主体隔离 | 🔴 无组织概念，principal=anonymous | 无租户/主体级强隔离 |
| Space 业务域+本体绑定 | 🟡 Gaia 一个 Ontology 独立存在，无 Space 容器层 | 无业务域容器，本体无生命周期绑定 |
| Project 安全边界+代码数据同栖 | 🔴 无 Project 概念，ObjectType 直接属 Ontology | 无协作安全边界，无代码数据同栖约束 |
| Marking MAC 强制兜底 | 🔴 无标记体系 | 无数据级强制访问控制 |
| 行/列级安全（Restricted View） | 🔴 ObjectQueryService filter 不感知权限，无行级下推 | 无千人千面，查询层无权限下推 |
| Group 组为核心身份 | 🔴 无 Group，无 User 模型 | principal=anonymous，无身份体系 |
| 四级角色体系 | 🟡 ActionAuthorizer（ADR-011）有 Action 三层权限（执行/行级写/参数级）存 ActionType.parameters.permissions JSON，无独立 ORM 表 | 仅 Action 层雏形，无 ObjectType/Property/Function 层权限 |
| 中心化授权引擎 | 🔴 无统一授权引擎 | 各 Service 各自校验，无统一 PEP/PDP |
| 审计治理 | 🔴 audit 只写日志无审计表，principal=anonymous | 无审计入库，无治理工具 |
| Gravitino RBAC | 🟡 Gravitino 自带 check_access | 仅物理资产层，不到 ObjectType/Property 层 |

### Gaia 落地的关键裁剪考量（设计时必须决策）
1. **Gaia 无 Spark/Transform/Foundry 应用体系**：代码数据同栖、Reference、Workshop 应用角色等概念需重新映射或舍弃
2. **技术栈不同**：PG（元数据+object_state）/ Doris（在线读主源）/ Iceberg（全量明细）/ Trino（联邦）/ Neo4j（图）—— 权限下推要分别考虑各引擎能力（Doris 行级权限、PG RLS、Trino 联邦权限传递）
3. **定位差异**：Gaia 是开源本地优先，Palantir 是企业 SaaS —— 多租户/组织隔离的强需求程度不同，需评估是否做完整 Organization 层还是降级
4. **已有底座可复用**：ActionAuthorizer（三层权限）+ object_state（OCC）+ outbox（副作用）+ AnalysisRecordStore（证据链）+ ActionExecutionLog（CDL 审计雏形）—— 决策捕获与权限可共用底座
5. **Scenario 设计已就绪**：`scenario-*.md` 三份设计文档已设计 object_state 加 scenario_id 维度 —— 权限设计需与 Scenario 的 overlay 读写语义协同（scenario 内的权限边界）
