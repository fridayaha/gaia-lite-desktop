# 工程能力证据沉淀规范

## 1. 目标

Hub 每个重要功能不仅要交付代码，还要同步沉淀设计、测试、演示和可量化结果。这些材料服务于：

- 架构评审与方案复盘；
- 开源展示与技术分享；
- 岗位能力证明；
- 团队知识传承。

---

## 2. 八类能力方向

| 方向 | Hub 对应能力 | 推荐沉淀材料 |
|------|-------------|-------------|
| Agent / Skill / Tool / MCP 资产建模 | 统一治理模型、四类资产 Schema、Manifest Spec | 数据模型设计文档、类型校验案例 |
| Runtime Discover / Resolve | 能力发现与解析接口、依赖递归展开 | API 设计文档、Resolve 示例、循环检测方案 |
| 权限、审批、生命周期治理 | RBAC 角色权限矩阵、生命周期状态机、审批流 | 权限矩阵文档、状态流转图、拒绝案例 |
| Agentic Asset Security / 安全准入 | 安全扫描、规则引擎、风险分级阻断 | 扫描规则表、blocking 阻断案例、ScannerAdapter 设计 |
| 工具 / MCP / Runtime 适配 | OpenAPI→Tool 导入、Tool→Function Calling 导出、MCP Config 校验 | 导入导出示例、兼容性矩阵 |
| 可观测性与审计 | request_id、access log、事件日志、审计记录 | 日志设计文档、审计链路示例 |
| 后端工程化质量 | FastAPI + SQLAlchemy + Alembic + 测试覆盖 | 测试基线、pyproject.toml、CI 友好结构 |
| 技术方案表达 | 方案设计文档、Roadmap、集成设计 | 主方案 doc、平台集成 doc、RBAC 设计文档 |

---

## 3. 功能完成检查清单

每个重要功能完成后，检查以下项：

| 检查项 | 说明 |
|--------|------|
| 解决了哪个平台问题？ | 一句话描述业务价值 |
| 属于哪类能力方向？ | 从八类能力中选择 |
| 是否有设计文档？ | 方案设计或 API 设计 |
| 是否有测试覆盖？ | 新增测试数、总测试通过率 |
| 是否有日志 / 审计？ | access log / event log 覆盖 |
| 是否有权限边界？ | 权限检查是否正确拒绝未授权请求 |
| 是否有失败场景覆盖？ | 异常、404、403、409、500 测试 |
| 是否有安全风险说明？ | 已知风险、缓解措施 |
| 是否有可演示路径？ | curl 验证步骤或 Demo 指南 |
| 是否有可量化结果？ | 测试数、覆盖率、端点数、角色数等 |
| 是否有项目价值总结？ | 一句话表达此项对平台的贡献 |

---

## 4. 不放入仓库的内容

以下内容明确不进入 Git 仓库：

- 个人简历、面试问答、求职材料；
- 未授权截图、内部文档原文；
- Token / 密钥 / 密码 / API key / 私有地址；
- OpenCode 本地配置（`opencode.json`、`.opencode/`）；
- 本地 agent 临时文件（`.agent/`、`.agent-cache/`）。

---

## 5. 目录规范

```
docs/engineering_evidence/
├── README.md                          # 本文档
├── feature_evidence_template.md       # 功能证据模板
└── (后续按功能建子目录，如 rbac-2/)
```

子目录在对应功能真正复盘时按需创建，名称使用 `{feature-key}/` 格式，内容包含该功能的完整证据材料。
